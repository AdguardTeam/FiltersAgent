This report is a FALSE POSITIVE (incorrect blocking): filtering broke legitimate page functionality, and the fix restores it without disabling legitimate filtering.
Treat the user-provided issue screenshot as the primary definition of the broken functionality; reporter annotations identify the exact affected region.
Investigate the mechanism, not just the pixels: reproduce the breakage with the prepared baseline first, then name the rule behind it. `get_applied_rules`, when the prepared session offers it, lists every rule the engine applied to the page with its list — the rule behind a blocked request, a hidden element or an injected scriptlet, including rules from lists outside this repository. Decide which of them breaks the page; when the applied rules alone do not settle it, diff `get_network_log` between the unfiltered and prepared sessions (blocked requests report status 0), read `get_console_log` for ERR_BLOCKED_BY_CLIENT and failed loads, and halve the lists as the task describes. `search_rules` for the culprit then shows its family in this repository. The blocked host is usually a third party, not the reported page domain.
Candidate preference, mirroring maintainer practice: first a narrowly scoped exception — network `@@||blockedhost/path$domain=<reported-site>` or cosmetic `<reported-site>#@#selector` — always pinned to the reporting site; second, when the breakage comes from a half-handled banner or an over-broad block, a more precise replacement rule or a gentle scriptlet (for example `prevent-xhr`) instead of an exception. Never propose a global exception without a domain scope.
If the breakage does not reproduce, is caused by DNS-level filtering outside this scope, or duplicates an already-fixed report, finish with `analysis_only` and say so plainly — about half of real incorrect-blocking reports need no rule change at all.
In the `apply_rule` experiment, phase B must show the breakage and phase C must show the functionality restored without new advertising appearing anywhere on the page. Pass `symptomDescription` to `apply_rule` naming the breakage you proved live — the element or content filtering removes and where it sits. A reporter screenshot usually cannot show a breakage, because what defines it is what is missing, so without your description the phase sessions may judge a symptom that never reproduces.
A `#@#` exception cancels only a rule carrying the SAME selector text; a more specific selector cancels nothing. `.ad-sidebar` and `aside.ad-sidebar` match the same element but are different rules, so write the exception with the culprit selector exactly.
Generic rules compiled from imported upstream lists are absent from this repository, so `search_rules` cannot show you the culprit line; `get_applied_rules` shows it with its list. When no session offers it, or it names no rule hiding the element, recover the selector from the hidden element's own attributes and from `search_rules` by selector: an existing `othersite#@#<selector>` exception family proves the generic rule text.
